Type judgments for a subset of OCaml, monomorphic and polymorphic.
Published

September 30, 2026

First, we specify a subset of the OCaml grammar subset. Associativity and precedence are not described here, and a description can be found in the Bison grammar picoml-stepper/interpreter/picoml.y.

This note will describe the static semantics of our language. In particular, each expression has a type \(\tau\) of possible data values. Our (sound) type system will a type for each expression, such that the dynamic value will always be in the type of \(\tau\).

Towards this, the main rule is the type judgment.

where \(\Gamma\) is our type environment (a context mapping variables to types), \(e\) is an expression, and \(\tau\) is some type. Then, under the type environemnt and a set of preconditions (above the bar), then we prove that \(e\) has type \(\tau\). A sound program has expressions for which the judgement \(\emptyset \vdash e : \tau\) is derivable. We will use \(\Gamma_1 + \Gamma_2\) to denote \(\Gamma_1 \cup (\Gamma_2 \setminus \Gamma_1)\) (note that this is not commutative).

Note that this is closely related to the idea of a logic system. Types correspond to propositions, and terms correspond to proofs. This is known as the Curry-Howard isomorphism; we will see that functions correspond to implication, and application corresponds to modus ponens.

A monomorphic type system

First, we give the rules for a very simple type system, in which each variable provably has a unique type. In contrast, a polymorphic type system can give a variable distinct types, as we will see later.

let x = fun y -> y + 2;;

Under our type system, we will assign \(x\) the type \(\textsf{int} \mapsto \textsf{int}\). Informally, if \(x\) is the type \(\textsf{int} \mapsto \textsf{int}\), then the binder \(y\) gets type \(\textsf{int}\), and the \(+\) operator will also return an integer. This is an example of a type derivation, and we will now provide judgements for proving the type of an expression (though we do not show soundness or completeness).

A polymorphic type system

The type system described above is very limited. Consider for example, the following expression:

let id x = x in (id 1, id false)

What type is \(\texttt{id}\)? For the first element of the pair, it seems like we need \(\texttt{id}: \textsf{int} \to \textsf{int}\), but for the second element, it seems like we need \(\texttt{id}: \textsf{bool} \to \textsf{bool}\). We need a more powerful type system to express the possibility for \(\texttt{id}\) to be both!

let id x = x

We see that OCaml gives \(\texttt{id}\) the type signature 'a -> 'a It is instructive to think of this as sugar for the universally quantified type \(\forall(\alpha . \alpha \to \alpha)\). We read this as the type is now a function taking a type as an argument, and in general denote as \(\forall(t . \tau)\).

In this system, beyond our basic and compound types in the monomorphic type system, we also introduce type variables (in OCaml, prefixed with a ', and in our mathematics, we use lowercase greek letters). Finally, every type has a universal quantifier dictating the bound variables.

The second judgment that must change is in assigning new variables in a let (i.e. modifying the type environment); we need to be able to create polytypes from monotypes. To do this, consider a new function

\[ \mathbf{Gen}(\tau, \Gamma): \textsf{Monotype} \times \textsf{Environment} \to \textsf{Polytype} \]

which will bind all the free variables in \(\tau\) that are not in \(\Gamma\). Namely, the free variables of monomorphic types are the type variables, of polymorphic types must remove the quantified vars, and for an environment, all free variables over the range.

And for the final example, we note that the following does not type check.

let rec f = fun x -> f (x, x);;

Indeed, we fail at the argument of the recursive call.

The type of \(f\) is not quantified inside its own body, so its input type is fixed to \(\alpha\). The premise \(\left\{ x: \forall . \alpha, f: \forall . \alpha \to \beta \right\} \vdash (x, x) : \alpha\) has no derivation: the pair rule only derives \((x, x) : \alpha * \alpha\), and no monotype \(\alpha\) is equal to \(\alpha * \alpha\).

The above is a case of our type system not allowing polymorphic recursion. However, OCaml does allow this when the types are explicitly written. Apparently, polymorphic recursion makes type inference undecidable.

let rec f: 'a . 'a -> int = fun x -> f (x, x);;

Indeed, this can be very powerful. Consider the following representation of a perfect binary tree, with values at the leaves.

type 'a perfect = Leaf of 'a | Node of ('a * 'a) perfect;;

We might want to find the depth for a perfect tree. A typical way might be to use mutual recursion for the two cases. However, it is more elegant to use the same depth function that is polymorphic, from a 'a perfect to ('a * 'a) perfect in the recursive call.

let rec depth : 'a . 'a perfect -> int = fun t -> match t with | Leaf _ -> 0 | Node t -> 1 + depth t in let t = Node (Node (Leaf ((1, 2), (3, 4)))) in depth t;;
